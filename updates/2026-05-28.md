Read and analyzed `claw-code-main` — a Python + Rust port of Claude Code's internal source.

### Documents created

- **`ARCHITECTURE_COMPARISON.md`** — plain-language comparison of Claude Code vs Glitool architecture, what each does better

### Key findings

Claude Code is one universal agent with unlimited tools. Glitool is a router sending to specialist agents. Each approach has tradeoffs — documented in ARCHITECTURE_COMPARISON.md.

Claude Code's prompts are shorter and tighter than Glitool's. Four key rules we're missing:
- "Diagnose before switching approach"
- "Report outcomes faithfully — if verification failed, say so"
- "No speculative abstractions beyond task scope"
- "Carefully consider blast radius"

## 2. Git Context Auto-Injection

**File:** `CLI/src/agent.ts`

Added `getGitContext()` function that runs `git --no-optional-locks status --short --branch` before building the system prompt. Output is appended to every agent's system prompt so agents know which files are modified before calling any tools.

**Behavior:**
- Git repo with changes → git state injected
- Git repo, clean → injected (shows clean branch)
- No git repo → silently returns empty string, nothing injected
- Git not installed / timeout (3s) → falls back silently

**Saves:** 1–2 tool calls per session on projects with active changes.

## 3. bashTool Schema Fix

**File:** `CLI/src/tools/bashTool.ts`

**Problem:** LLM consistently passed `timeout` as string `"120000"` and `runInBackground` as string `"false"`. Zod rejected them → tool errored → agent looped 3× → hallucinated success.

**Fix:** Changed schema to accept both types via `z.union`, coerce to correct types inside function body with explicit type annotations.

```typescript
// Schema
timeout: z.union([z.number(), z.string()]).optional()
runInBackground: z.union([z.boolean(), z.string()]).optional()

// Function body
const timeoutMs: number = typeof timeout === 'string' ? parseInt(timeout, 10) : (timeout ?? DEFAULT_TIMEOUT_MS);
const bgMode: boolean = typeof runInBackground === 'string' ? runInBackground === 'true' : (runInBackground ?? false);
```

**Why `z.union` not `z.coerce.boolean`:** `z.coerce.boolean("false")` returns `true` because `Boolean("false")` is truthy in JS — any non-empty string is true. The union + `=== 'true'` approach handles it correctly.

## 4. readFileTool Schema Fix

**File:** `CLI/src/tools/readFileTool.ts`

**Problem:** Schema had `.transform()` at the schema object level to handle `path`/`filename` aliases. LangChain cannot serialize `.transform()` to JSON Schema → "Transforms cannot be represented in JSON Schema" error → coder agent crashed on startup before running any tool calls.

**Fix:** Removed `.transform()` from schema. Moved alias resolution into function body.

```typescript
// Before (broken)
schema: z.object({ filePath, path, filename }).transform(o => ({ filePath: o.filePath ?? o.path ?? o.filename ?? '' }))

// After (fixed)
schema: z.object({ filePath, path, filename })  // flat, no transform

// Function body
async ({ filePath, path: pathAlias, filename }) => {
    const resolvedPath = filePath ?? pathAlias ?? filename ?? '';
```

**Rule learned:** Never use `.transform()` on LangChain tool schemas. Coerce inside the function body. Schema must be flat and serializable to JSON Schema.

## Issues Found (Not Yet Fixed)

### Issue 1 — editFileTool alias mismatch

**Symptom:** LLM calls `editFile` with `{ filename, content }` but schema expects `{ filePath, oldString, newString }`.

```
Error: expected string, received undefined → at filePath, oldString, newString
```

**Fix needed:** Same pattern as readFileTool — accept `filename`/`path` as alias for `filePath` inside function body. Also need to handle `content` for cases where the LLM wants to write a whole file.

**File:** `CLI/src/tools/editFileTool.ts`

---

### Issue 2 — readFileTool error messages still use old variable

**Symptom:** After the schema fix, error messages inside the function still use the old `filePath` variable instead of `resolvedPath`. When LLM passes `filename`, `filePath` is `undefined` → "File not found: undefined".

**Fix needed:** Replace every `${filePath}` in error message strings with `${resolvedPath}`.

**File:** `CLI/src/tools/readFileTool.ts`

---

### Issue 3 — cwd problem with scaffolded projects

**Symptom:** `npx create-next-app@latest portfolio --yes` creates project at `testportfolio/portfolio/`. All subsequent `bash` calls run from `testportfolio/` (parent). `npm run dev` fails with "Missing script: dev" because it's looking in the wrong directory.

**Root cause:** Planner doesn't add a step to set `cwd` after scaffolding. Coder runs all commands from the original working directory.

**Fix needed:** Add a rule to coder/planner prompts: "After scaffolding a new project into a subdirectory, all subsequent commands must use `cwd` pointing to that subdirectory."

---

### Issue 4 — PayloadTooLargeError on server

**Symptom:** `PayloadTooLargeError: request entity too large` — tool output blobs pile up and exceed Express's default 100KB body-parser limit.

**Fix needed:** In `server/src/index.ts`, increase body-parser limit:
```typescript
app.use(express.json({ limit: '10mb' }));
```

---

### Issue 5 — Agent hallucinating success after tool failures

**Symptom:** After failing 3× with editFile errors, LLM responded:
> "I have created a new Next.js project and verified the project structure."

Nothing was actually created. This is a prompt problem — no rule forces honest reporting.

**Fix needed:** Apply the "Report outcomes faithfully" rule from `PROMPT_ENGINEERING.md` to the coder agent's response style block.

---

### Issue 6 — LLM inventing tool names

**Symptom:** Model called `runShell` which doesn't exist → "Tool not found" error.

**Fix needed:** Add available tool names to coder system prompt description or tool list header so the model knows exactly what tools exist.
